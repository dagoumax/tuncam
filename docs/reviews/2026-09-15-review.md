## P1：连续采集缺少无帧看门狗

位置：`src/tucam_control/camera_process.py:233`、`:255`；`ui/main_window.py:155`。

等待队列超时仅返回 None，既不检查 SDK 进程存活，也不判断距离上一帧是否超出曝光时间和传输余量。采集中 connection_status 固定返回 None；定时设备刷新也跳过采集中状态。SDK 等帧接口或遥测读取挂起、子进程异常退出时，无法依靠 RPC 超时机制自动发现。

内存模拟：进程存活状态为 False、帧队列为空时，得到 frame=None、error=None、capturing=True、connection=None。

建议：独立监控进程存活及最后成功帧时间，按曝光时间设置无帧期限；异常统一结束会话、更新本地/远程状态并回收 SDK 进程。真实驱动挂起仍需故障注入验证。

## P1：新采集会话可能收到旧帧

位置：`src/tucam_control/camera_process.py:127`、`:215`、`:229`。

帧队列只在创建 SDK 进程时初始化，停止和重新开始均不清空；帧事件也没有采集会话 ID。队列里残留的旧帧会由新 CaptureWorker 按新 generation 发给主窗口，可能被保存为新图像、重新计算并附上当前时间。

内存模拟：预置 previous_session_frame 后执行 start_capture，新一轮第一次 wait_for_frame 返回该旧帧。

建议：为 SDK 帧、主窗口帧和处理结果贯穿同一会话标识；停止完成后排空旧队列，接收端再次验证会话。

## P1：停止采集不取消旧处理结果

位置：`src/tucam_control/ui/main_window.py:1113`、`:1784`、`:1884`。

真实采集停止只更新 capture_generation，没有递增 processing_generation，也未清空 pending_frame。正在计算的旧结果仍会进入浓度历史，随后继续提交旧 pending_frame。普通停止、手动急停、保存报错停止均经过此路径。批量停止已有对应清理，但真实采集没有。

内存模拟：stop_success=True、camera_capturing=False，同时 processing_generation 仍为 9，pending_frame 仍存在。

建议：停止时作废本轮处理结果并清空待处理帧；按业务要求明确最后一帧是否接纳，并保证它的原始时间戳及会话归属。

## P1：主线程仍执行阻塞采集与磁盘写入

位置：`src/tucam_control/ui/main_window.py:975`、`:915`、`:1153`。

单帧按钮直接调用 capture_single，主线程等待整段曝光及 SDK RPC。连续采集回调直接调用 Pillow.save，目录创建也在主线程执行。慢盘、网络目录或设备 I/O 卡住时，曲线和急停按钮无法及时响应。保存异常自动停止只有在 I/O 返回异常后才会执行，不能解决写入阻塞。

建议：单帧采集也采用异步状态机；保存使用有界后台队列并明确队列满、写盘超时、磁盘满时的停止策略。

## P1：长时间高采样率导出会阻塞界面并大量占用内存

位置：`src/tucam_control/ui/concentration_tab.py:1332`、`:1378`、`:1468`。

导出在 UI 槽函数中完成。每条序列先生成全部插值值和 datetime 列表，再将全部序列保留在 prepared 后写 CSV。15 探头 × 4 气体 × 1 小时 × 1000 Hz 对应约 2.16 亿个序列样本，Python 对象内存远大于原始数值数组。可能长时间无响应或耗尽内存。

此项由分配方式与数据规模确认，没有实际执行巨量导出来压满本机。

建议：在后台按时间块插值并流式写出，加入进度、取消、规模预估和临时文件原子替换。

## P1：停机区间被本地导出插值填满

位置：`src/tucam_control/ui/concentration_tab.py:439`、`:968`、`:1468`。

mark_history_gap 只通知统计 tracker，没有在浓度历史中存储分段标记。曲线和 PCHIP 仍使用停机前后的点；远程端已有独立 gap 事件，因此本地和远程的断点语义不一致。

复现：10:00:00 测量 10%，停止，10:01:00 测量 20%；1000 Hz 导出生成 60,001 行，并在未采集的 10:00:30 给出 15%。

建议：历史明确记录会话/断点，曲线和导出仅在同一连续区间内插值。

## P1：多探头 CSV 按行号而非时间合并

位置：`src/tucam_control/ui/concentration_tab.py:1403`。

各序列独立筛选和重采样，但输出时从第一条序列取 times[i]，将其他序列的 vals[i] 放到同一行。中途新增探头或重新启用旧探头导致时间轴不一致时，会静默错配时间。

内存 CSV 复现：A 在 10:00:00/01 的值为 10/11，B 在 10:00:10/11 的值为 20/21。输出却把 B 的 20/21 标在 10:00:00/01。

建议：按时间戳联合对齐，在合法连续区间内插值，缺失位置留空。

## P2：设置重处理会新增并不存在的新测量点

位置：`src/tucam_control/ui/main_window.py:1625`、`:1812`、`:1990`。

应用设置总会将缓存的最后一帧重新排入处理队列。处理完成统一使用 datetime.now，并推进信号诊断、平滑、历史和远程测量序号。停止后仅修改显示配置或探头名，也可能把同一图片再次当成真实采样；连续操作还能影响“三帧失效/两帧恢复”的计数。

真实帧也未从获取时刻携带时间戳，处理延迟会反映到统计时间。当前行为与文档中的“处理完成时间”一致，但不等同于曝光/帧获取时间。

建议：区分真实测量事件和重计算事件，携带采集时间及 frame_id；重计算只替换展示，不增加样本或诊断帧数。

## P2：扩大统计窗口不能恢复已有历史样本

位置：`src/tucam_control/threshold_statistics.py:55`、`:147`。

样本在每次更新时按当前 N 永久删除。窗口从 2 秒调到 60 秒，虽然浓度历史还保留更早数据，tracker 却只剩 2 秒数据，表头立即显示 60 秒。

复现：连续记录 t=0..10 共 11 个值，2 秒窗口剩 3 个；扩大到 60 秒后仍只有 3 个，均值为 9，而全部已有 11 个值的均值应为 5。

建议：从统一历史重新构建窗口，或维护独立于展示窗口的有界保留策略；历史不足时明确显示有效覆盖时长。

## P2：清除或重算本地历史没有同步远程历史

位置：`src/tucam_control/ui/concentration_tab.py:1211`；`ui/main_window.py:449`、`:1619`。

浓度页清除按钮仅调用本地 clear_history。气体或平滑设置变化同样只清本地历史；remote_server.reset_measurements 目前仅在载入新批量测试时使用。浏览器可能继续显示清除前或旧算法下的值，并与新值连接。

建议：把历史重置提升为主窗口的统一操作，同时重置本地 tracker、远程 stream_epoch 和浏览器数据。

## 后续工程改进

- 长期运行：本地原始/平滑历史列表无限增长；大统计窗口的均值和标准差每次全量扫描。建议统一历史存储与分层保留，使用增量统计。
- 配置与远程：save_user_settings 将 remote_token 写回 Git 跟踪的配置文件。上次提交人工排除了令牌，但保存设置后仍会出现，需将本机凭据单独存放。现有 HTTP 仅适用于可信隔离局域网，跨网需求应另行设计。
- 设置应用：相机参数写入失败被收集到诊断后，外层仍可能继续恢复采集并保存期望值；应区分期望值、读回值和应用成功状态。
- 诊断可用性：自动测试会写入实际 logs，产生模拟 SDK 错误和 OpenGL 失败信息。本次测试后的日志不能直接作为现场故障证据，建议测试默认使用临时日志目录并记录会话/进程身份。
- 测试覆盖：现有 118 项主要验证模块正常路径，缺少无帧挂起、旧队列残帧、停止后晚到结果、写盘阻塞、断点导出、异步时间对齐等集成用例。
